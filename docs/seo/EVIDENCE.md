# Capability evidence audit (SEO-3, read 2026-11-15)

The honest record behind `src/lib/seo/capabilities.ts`. Every wave-1 page leans on a capability in that file; this page says what each one is, on which surface, and why.

## How it was judged

- **Running code only.** A registered route, a service, a scheduled cron, a Shopify extension in the app config, or a screen that calls them. Docs, plans, comments and tests are not evidence. Four repos were read: peakhour-api (it also holds the Shopify app config and the extensions), peakhour-shopify, peakhour-b2c and peakhour-wordpress. Every evidence path below exists on master and was opened.
- **Status is what a merchant on production can use today.** A provider hard-coded `coming_soon` in production, or a catalog row that is `coming_soon` or `in_development`, means not live even when the code is complete. The built code is kept in the evidence and the reason it is not live is in the limitations.
- **Claims are written only for what the code proves**, in a merchant's words, one sentence each. A partial capability gets the narrower claim.

## Catalog sources, and one gap

- **Production integrations** come from the public API, `GET https://api.peakhour.ai/v1/platform/catalog` (status per key). Production wins over dev: `google_ads`, `gsc`, `linkedin_ads` and `wordpress` are `coming_soon` there and `live` or available on dev.
- **Features (`cfg_features`)** come from the dev database. **The production database read was refused by the permission system**, and no public endpoint lists feature statuses, so production `cfg_features` was not read directly. The plan's own 2026-11-15 production reading (section 2.4) agrees with dev on the points that matter: `support.ai_replies`, `support.channels_core`, `support.channels_all`, `support.assignment` and `support.sla` are `coming_soon`; `support.inbox` and `commerce.woocommerce.*` are `active`. `src/lib/seo/catalog-snapshot.json` labels each entry `prod-public-api` or `dev-db`. Re-run the drift script against production once before the production release.
- Production's public list omits `shopify`, `google_business_profile`, `messenger`, `instagram_dm` and `x_dm`. Missing means off for the three message channels (the code fails closed). For `shopify` and `google_business_profile` it is a question; see "Needs the owner".

## Settled drifts

- **Support channels.** `support.channels_core` and `support.ai_replies` are `coming_soon` in the catalog, but the code runs WhatsApp and website-chat support, suggested replies and the inbox, and nothing in code gates them on those keys. Recorded as status `development` with no claim, and the limitation says it is built but not yet switched on for merchants (plan Q3 is the owner's call). `/support` no longer names `support.channel_inbox`; SEO-7 rewrites its copy.
- **Google Ads.** Built (Search, Performance Max, Demand Gen, targeting, bidding, reports, a conversion sweep) but `google-ads.provider.ts` sets `availability: resolveIsProd() ? "coming_soon" : "available"`, so connect and authorize return COMING_SOON in production, and the production catalog agrees. The adapter is marked not live-tested. Status `development`, no claim.

## Needs the owner

1. **Shopify as a whole.** The production product catalog reports the Shopify channel `live`, so Shopify capabilities are recorded `live`. But `shopify.provider.ts` is hard-coded `coming_soon` in production, and `shopify.app.toml` still points at the dev hosts. If the Shopify app is not yet promoted to production, every Shopify record should drop to `beta`. This changes no page today, because the site is behind the coming-soon gate.
2. **Google Business Profile.** Writes to Google are held by a database switch that ships off (`cfg_presence_networks.writesEnabled`, migration 943) and the production value could not be read; the integration row is absent from production's list. Recorded `beta`, claims narrowed to preparing changes for approval.
3. **Peakhour Summit** runs only when its CMS skill templates are active; recorded `beta` for the same reason.
